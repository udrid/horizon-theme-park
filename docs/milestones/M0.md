## 1. Goal, in plain words

Prove the whole road from our code to the game once, with the smallest possible content:

1. A tiny, real piece of game-free code in `park-core` decides *when* to say "Horizon Theme Park loaded".
   `cargo test` checks it in seconds.
2. A small tool, **`park-bundle`**, glues `park-core` into **one file**, `park.rs`, for the game. A test
   compiles that file the way the game will, so mistakes show up in seconds instead of in a 6-minute build.
3. A thin native mod built from it says **"Horizon Theme Park loaded"** in chat when you enter a world.

No roller-coaster code yet. After M0, every milestone only adds code to `park-core` (and a few lines of glue).

## 3. What changed from the draft

1. **When the message is said (F1–F3).** The draft said it at "world open ready". By the code, nobody is in the
   world yet then, so you would likely see nothing in chat. New proposal: say it on the first tick that has a
   player in the world (choice C3).
2. **File attributes are refused (F4).** The draft dropped `#![…]` but missed `//!` comments, which would have
   broken the first game build. `park-bundle` now turns `//!` into `//` and refuses `#![…]` with a clear message.
3. **Follow `mod` lines, don't read every file.** The draft read `park-core/src/**/*.rs`. Following the
   `mod name;` lines from `lib.rs`, as Rust itself does, keeps `pub`/private and nesting right and skips stray files.
4. **Keep the test blocks** instead of cutting them out (C2). The game never compiles test-only code, and cutting
   it needs fragile "where does this block end?" logic.
5. **A compile test for the glued file** (C5): park-core's tests run a second time *through the glued copy*, at
   the same `crate::game::htp_park::` paths the game uses. A gluing mistake costs seconds, not a 6-minute build.
6. **Edition 2024 (F7, C7)**, so `cargo test` judges our code by the same rules as the game.
7. **Line endings (F11)**: the tool treats Windows and Linux line endings alike, so the "stale" check can't fail
   on your PC while passing in CI.
8. **Two new rules for `park-core`** from F7–F8 (section 6): no library feature Horizon lacks (this matters for
   saving at M3), and no `env!`, which would read Horizon's values inside the game.
9. **Layout copied from the spike:** `compatibility.json` sits in `mods/native/`, one helper file per hook.
10. **Docs sync is smaller (C6):** the Host trait is redesigned in the M1 plan, where code and tests use it.
11. **Order:** commit the current docs first (C4), so M0's commits stay small and readable.

Kept from the draft: the pin, the module mechanism, `--check` in CI, the dev-log draft, the cost notes.

## 6. New rules for code in `park-core` (added to ARCHITECTURE §2 as 7–11, in T7)

These follow from D8 and the facts above. `park-bundle` enforces 7, 8 and 11; the compile test (T4) and
edition 2024 cover the rest.

7. **No file attributes** (`#![…]`) (F4). `//!` comments are fine; the tool turns them into `//`. Crate-wide lint
   settings go in park-core's `Cargo.toml` instead.
8. **No `env!`, `option_env!`, `include!`, `include_str!`, `include_bytes!`, `#[macro_export]` or
   `extern crate`.** In the game, `env!("CARGO_PKG_VERSION")` would quietly give Horizon's version, and an exported
   macro would leak out of our module.
9. **Modules are declared on one line** (`mod name;` or `pub mod name;`, attributes on the lines above), with the
   file at `name.rs` or `name/mod.rs`. Inline `mod name { … }` blocks are fine.
10. **Turn on no library feature Horizon lacks** (F8). Horizon's `glam` has no `serde` support, so `DVec3` can't be
    saved by `serde` directly: saved files use plain arrays like `[f64; 3]`. The M3 plan designs those file types.
11. **Never write `crate::` inside a text string**: the tool would rewrite it.

## 7. Tests and checks

- Everyday checks (CLAUDE.md): `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo fmt --all --check`, `cargo run -p park-bundle -- --check`.
- **welcome (T1):** silent while nobody is here; says the message exactly once when someone arrives; silent after
  that; says it once more after `world_opened()`; the text is exactly `Horizon Theme Park loaded`.
- **park-bundle (T2–T3), on a sample tree in `tools/park-bundle/tests/`:**
  1. Same input twice gives byte-identical output.
  2. Windows line endings in give the same output as Linux ones.
  3. Nesting: `mod a;` → `a.rs`; `pub mod b;` → `b/mod.rs`; `mod c;` inside `b` → `b/c.rs`; `pub` and the
     attributes above each `mod` line (like `#[cfg(test)]`) are kept.
  4. Every `crate::` becomes `crate::game::htp_park::`; `my_crate::` and `$crate::` are left alone.
  5. `//!` becomes `//`.
  6. Refused, with file and line: `#![`, `#[path`, `include!`, `include_str!`, `include_bytes!`, `env!`,
     `option_env!`, `#[macro_export]`, `extern crate`; a missing module file; both `x.rs` and `x/mod.rs`.
  7. The output has none of the refused items and no `crate::` outside the new prefix (the MILESTONES test).
  8. `--check`: fresh → exit code 0; one changed character → exit code 1 and the message; line endings only → fresh.
  9. The module name in `horizon-mixin.toml` is `htp_park`, matching the prefix.
- **Compile test (T4):** the glued copy builds as `crate::game::htp_park` and the welcome tests pass through it.
- **In game (T6):** scratch world first, then your new test world: the line appears in chat when you enter, once,
  and in the log next to the world-open line.

## 8. Choices for you (nothing is built until you answer)

**C1. The mod's id.** It shows in the build output and the logs.
- **A. `horizon-theme-park`**: matches the repo and the mod folder, and hyphens are allowed (F6). **Recommended.**
- B. `horizon_theme_park` (the draft's pick): same words, but differs from the folder name.
- C. `htp`: short, matches our entity tag (D20), but cryptic in a list of mods.

The module names inside the game stay `htp_park` and `htp_glue` either way (S2).

**C2. How `park-bundle` reads Rust, and what it does with test code.**
- **A. A small text tool, no outside libraries, that keeps test blocks as they are.** Nothing to download, about
  200 lines you can read. Test-only code is never compiled in the game, so keeping it costs nothing, and it lets C5
  run every test through the glued copy. Unusual code could fool it, but the compile test catches that.
  **Recommended.**
- B. The same tool, but cutting test blocks out (the draft). Needs a "tests go last in each file" rule and fragile
  "find the end of the block" logic, for a slightly smaller file.
- C. Use `syn`, a library that reads Rust exactly like the compiler. Most robust; under 1 MB to download; much more
  code to read. We can switch to C later if A ever bites.

**C3. When the "loaded" line is said.**
- **A. On the first tick with a player in the world: once in chat and the log, plus a log line at world open.**
  It uses both hooks M1 needs anyway (world open and tick), and the "say it once" logic sits in `park-core`, tested
  by `cargo test`. **Recommended.**
- B. At "world open ready" (the draft). Simplest, but by F2 it would most likely reach only the log, so no chat
  line for the dev-log.
- C. Privately to each player as they arrive, so LAN friends see it too. Needs memory of who was greeted, which is
  more than M0 needs.

**C4. The uncommitted docs and the `spike/` folder.**
- **A. Commit the docs now in two small commits** (decisions, architecture and glossary; spike write-ups, research,
  issue drafts and the handoff), and add `spike/` to `.gitignore` so it can't be committed by accident.
  **Recommended.**
- B. The same commits, but move `spike/` out of the repo (to `..\horizon-theme-park-spike\`). A cleaner repo, but
  its scripts' paths break.
- C. Leave everything uncommitted until M0 is done: one big pile, and easier to lose work.

The approved M0 plan and the new decisions get their own commit. Pushing stays yours.

**C5. Checking the glued file before the game build.**
- **A. A test in `park-bundle` compiles `park.rs` the way the game will and runs park-core's tests through it.**
  Seconds, no game. **Recommended.**
- B. Only the game build checks it (the draft). A gluing mistake then costs a 6-minute build to find.

**C6. How much of ARCHITECTURE.md to update in M0.**
- **A. Fix only plainly stale facts and add rules 7–11; mark the Host trait "redesigned in the M1 plan" and design
  it there**, where code and tests use it at once. **Recommended.**
- B. Rewrite the Host trait now (the draft's T6): design on paper with no code to test it, and M1 would likely
  change it again.

**C7. The Rust edition** (which version of Rust's rules our code follows).
- **A. Move the whole workspace to edition 2024, like Horizon.** Our tests then judge code by the game's rules.
  The crates are nearly empty, so there's nothing to fix; your Rust 1.99.1 supports it with no download.
  **Recommended.**
- B. Only `park-core` and `park-bundle` on 2024; `park-sim` stays on 2021. Works, but two rule sets are confusing.
- C. Stay on 2021 and keep a list of 2024 traps to avoid. Easy to forget one.
