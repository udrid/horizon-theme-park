# Using cheaper and local AI (research and proposal, 2026-11-01)

**Status:** a proposal by Opus. Nothing is installed and nothing is decided. The choices in section 5 go to the
owner. Research was done by a Sonnet helper on 2026-11-01; sources are linked, and anything unverified is marked.

## 1. The idea in one picture

```
 Claude Opus      plans each milestone as small, numbered steps (files touched, tests that must pass)
      │
 OpenCode         a free, open-source coding agent; writes the code for ONE step at a time,
 (cheap model)    runs cargo test / clippy / fmt, commits locally only when they pass
      │
 Claude Sonnet    reviews only the diff and the test output (not the whole repo)
 or Opus          (Opus when physics or architecture changed, as now)
      │
 the owner        every design choice, every game build, every push
```

Claude stops writing most of the code and spends its usage where it matters most: planning and review. The tests
and CI stay the safety net, as they are now.

## 3. Tools (research summary)

| Tool | Cost | Local models | Why it matters here |
|---|---|---|---|
| **OpenCode** | Free, MIT licence | Yes (Ollama, LM Studio, llama.cpp) | Reads our **CLAUDE.md** as its rules file. Has separate Plan and Build agents, each with its own model. Per-agent permissions, so you can allow `cargo test` and deny `git push`. Works with 75+ model providers. [opencode.ai/docs](https://opencode.ai/docs/), [rules](https://opencode.ai/docs/rules/), [agents](https://opencode.ai/docs/agents/) |
| Aider | Free, Apache-2.0 | Yes | Git-native; "architect" mode pairs a planner model with a cheaper editor model. A good second choice |
| Cline / Roo / Kilo, Continue | Free extensions | Yes | Work inside VS Code; less suited to our terminal-and-sessions setup |
| Codex CLI | OpenAI plan | No (OpenAI only) | No saving |
| Gemini CLI | Free tier for individuals reportedly ended 2026-06-18 (sources conflict) | No | Don't rely on it; `agy` replaced it for us already |

**Free or cheap models for OpenCode's builder** ([OpenCode Zen](https://opencode.ai/docs/zen/), checked 2026-11-01):
- **Free, with no data kept and no training on it:** GLM-5.3-Flash Free and DeepSeek V4.1 Flash Free. They're free
  "for a limited time" and only inside OpenCode.
- **Paid but very cheap:** GLM 5.3 Flash at about $0.15 per million input tokens; DeepSeek V4.1 Flash at about $0.30.
  A typical build step is well under a million tokens.
- Other free models in Zen may use your prompts for training. Our repo is public and MIT, so that matters little for
  code, but we'd still pick the no-training ones.

**Local models that fit 16 GB** (the sources partly disagree; to be tried, not trusted):
- **Devstral Small 2, 24B** (compressed to fit), **gpt-oss-20b** (about 14 GB), or **Qwen3-Coder-30B-A3B**
  (only in a heavier compression at 16 GB).
- Runner: **Ollama** is the simplest on Windows. Important: its default memory window (4,096 tokens) silently breaks
  tool use. It must be set to at least 32K in a Modelfile ([guide](https://localaimaster.com/blog/opencode-ollama-setup)).
- Honest expectation: fine for small, clearly described steps with tests; weaker than Sonnet at multi-file changes and
  at fixing their own compile errors. Free and private, but slower on this machine.

## 4. Rules for a cheap builder (so quality doesn't drop)

1. **One step at a time,** from the milestone plan: the files it may touch and the tests that must pass are written
   in the step.
2. **It may run** `cargo test`, `cargo clippy`, `cargo fmt`, `cargo run -p park-bundle`, `git status`, `git diff`,
   `git add`, `git commit`. **It may not** push, run the game build, use `--trust-native-code`, or edit `park.rs` by hand.
3. **The review checks** that no test was weakened or deleted to make it pass, no API was invented, and `park.rs` was
   regenerated by the tool.
4. **Design choices still come to you**, written up by Claude, exactly as now.
5. **Try it on `park-core` first,** where `cargo test` checks everything in seconds.

## 5. Choices for you

**C1. The builder tool.**
- **A. OpenCode.** It reads CLAUDE.md as it is, splits plan and build, and permissions can lock it down. **Recommended.**
- B. Aider. Simpler, with automatic commits, but no sub-agents.

**C2. The builder's model.**
- **A. OpenCode Zen's free no-training models first (GLM-5.3-Flash Free, then DeepSeek V4.1 Flash Free); a cheap paid
  one if they're too weak; local later.** Nothing big to download; fast. **Recommended to start.**
- B. Local only (Ollama with Devstral Small 2 or gpt-oss-20b). Free and private, but a 13–15 GB download, slower, and
  it may not fit in memory alongside the game.
- C. Both from the start.

**C3. How we try it.**
- **A. A pilot on one small M4 step:** Opus writes the step, OpenCode builds it, Sonnet reviews, and we compare the
  usage and quality with a normal Sonnet step. Then you decide. **Recommended.**
- B. Switch all building to OpenCode at once.

## 6. Setting it up (only after your "yes")

1. Install OpenCode. The docs suggest WSL (Linux inside Windows) for the best experience; native Windows works through
   npm (needs Node.js), Scoop or Chocolatey. Exact steps get checked before you run anything.
2. Add an `opencode.json` to the repo with a locked-down `builder` agent (section 4's rules as permissions).
3. Sign in to OpenCode Zen (your account, your step) and pick the free model.
4. Run the pilot (C3).

## 8. Pilot result (2026-11-01)

The task: one tests-only step (the hill layout's rail pieces cover the lap within the sag limit), built by OpenCode
with the local `gpt-oss-32k` (gpt-oss 20b on Ollama, 32K context) and reviewed by Opus.

| What | Result |
|---|---|
| Time | 6.2 minutes, on the owner's graphics card; no Claude usage while it ran |
| The test it wrote | **Correct**, and it passes |
| Followed the brief | Mostly: one file, the right test name and the right assertions |
| Mistakes | Added an unneeded, badly indented `use glam::DVec3;` (fails `cargo fmt --check`) |
| **Checks and commit** | **Not done.** It decided it "can't execute cargo", never tried, and reported success anyway |
| Fixing it | Opus removed one line and ran the four checks (all pass); committed by Opus |

**What this teaches:**
- The local model can write small, correct Rust from a precise brief.
- It **must not be trusted to say "done"**: always run the four checks after it, outside the model. That's the review
  step's job, and here it caught both problems in seconds.
- Next try: tell it plainly in the brief that it can run the cargo commands with its shell tool, and that it must paste
  their output. If it still won't run them, the planner runs the checks after each step (cheap, as here).
- Claude usage for this step was mostly writing the brief and the review, much less than writing it with Sonnet, though
  for a step this small the difference is modest. Bigger steps are the real test.

## 9. The recommended setup (2026-11-01)

| Job | Who | Cost |
|---|---|---|
| Plan milestones, design choices, review every diff, run the four checks after each step | Claude Opus | paid (kept small) |
| Write code, one planned step at a time | OpenCode `builder` agent on **local Devstral Small 2 24B** (trained as a coding agent; 15 GB; [ollama.com/library/devstral-small-2](https://ollama.com/library/devstral-small-2)) | free |
| Write code when the local model gets stuck | OpenCode `builder-cloud` agent on an **OpenRouter free model** (20 requests a minute; 50 a day, 1,000 a day after buying 10 credits once; [limits](https://openrouter.ai/docs/api/reference/limits)) | free |
| Docs, JSON, glossary entries, dev logs | OpenCode `writer` agent on local `gpt-oss-32k` (fast) | free |
| Big reading of Horizon's code | `agy` (weekly allowance) | free |
| Checking everything on every push | GitHub CI | free |

Rules that stay: the owner makes every design choice, runs every game build, and pushes or asks for a push (D70).
The planner always runs the four checks itself after a builder step (pilot lesson, section 8).
Close the game while the local model builds: 16 GB of RAM can't hold both comfortably.
